- **BR288Y-1620** [PVTC] 实现中 / Haiping Ye(alan) — 新增测量确认8G/8G2.5分频时钟为41.67MHz、4G2.5分频为50MHz，与DE换算值相符，且时钟jitter均为33ps、很稳定；结合此前function模式与DFT模式对比测试，初步确认时钟来源差异是影响BR Process/温度读数的关键因素；下一步需将测试版本升级为正式FW release以固化验证结论。
- **BR288Y-1621** [P2P] triage / Ethan Jiang — 已完成26颗die的批量测试验证：所有die使用外部156.25M晶振时钟均fail，但切换到内部时钟后可正常跑到25G，说明serdes本身功能正常。当前结论指向外部时钟输入路径或ext osc相关电路存在问题，具体根因尚待定位，需进一步分析外部时钟信号质量及相关配置。
- **BR288Y-1642** [Security] triage / Chao Wang(HW) — 目前尚无实质性调试进展，仅有HW同事Chao Wang在评论中建议在Tim创建的Jira BR288Y-1639下跟踪VGS测试状态。后续需在该Jira下跟踪Vgs Sensor glitch问题的测试与排查情况。
- **BR288Y-1651** [SW] triage / Botao Zhu — 已完成根因分析：确认group gemm随机mismatch是因tensor map在UB（uniform buffer）释放前被更新所致，分析结论已整理至Confluence文档。解决方案为用TMA nocp释放UB，并通过sc.wait确认UB读完后才更新tensormap。尚待回复确认是否仍为软件问题及使用哪个BU复现，后续需验证修复方案有效性。
- **BR288Y-1656** [SW] triage / Kerang Mao — 已完成问题复现与派发路径分析：确认N>4096时走cub radix sort（Histogram/ExclusiveSum/Onesweep kernel）路径，且在x86+NVIDIA CUDA上相同用例正常通过，问题与硬件/后端强相关；isa backend上偶现Chip error/SMMU fault/GCU error并伴随CTC potential hang（xid=257），mira backend版本可pass，且已提供full-stack包供复现验证。当前倾向为isa backend相关（软件或silicon待定），Bug已降级为high；尚待确认是软件还是silicon问题及具体失败率，需进一步定位CTC hang根因。
- **BR288Y-1669** [FW] triage / Hailong Jia — 已完成分析：确认掉卡时bootstage PCIE未init；从测试日志定位到最后一次Link Disable后cfg read RC Link Control寄存器超时12秒才读回，清link disable过晚触发FW的wait link up timeout机制，导致link后读EP配置空间回CRS。已验证：使用修改后的FW（去掉link down流程里的wait link up等待）测试Link Disable/Hot Reset间隔超过10秒再Enable均可正常建链枚举；并通过修改FW的CRS Release时间+测试工具验证Hot Reset和Link Disable可互相打断。当前结论指向FW link down流程中wait link up超时机制为根因，尚待确认修改后FW在完整混合Reset压测场景下复测通过并闭环。
